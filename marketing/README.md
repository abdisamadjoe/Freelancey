# Converted WordPress landing pages — Next.js

This project holds multiple independent SingleFile-capture conversions,
each mounted as its own route with its own header/footer/CSS:

- **`/`** — "CRM – Sierra WordPress Theme" (keydesign), converted from
  `../example.html`. See `src/app/(sierra)/`.
- **`/homepage2`** — "Sasflo – SaaS & App Landing WordPress Theme"
  (ThemeJunction), converted from `../example2-homepage2.html`. See
  `src/app/homepage2/`.

Each is a **separate Next.js root layout** (the "multiple root layouts"
pattern: `src/app/layout.tsx` was deliberately removed so every top-level
directory under `src/app` becomes its own root, with its own `<html>`/
`<body>`, global CSS, header, footer, and popup/menu state). They share
nothing but the Next.js/Tailwind tooling — no CSS or component leaks
between them, confirmed by testing both routes together. Navigating
between `/` and `/homepage2` is a full page load, not a client
transition, which is expected for this pattern.

Adding a third page follows the same shape: a new top-level folder under
`src/app/<name>/` with its own `layout.tsx` (root layout + header/footer)
and `page.tsx`, its own `src/app/<name>-globals.css` and
`src/styles/<name>/`, and its own `public/<name>/` for assets.

## Getting started

```bash
npm install
npm run dev
```

Open http://localhost:3000. `npm run build` produces a production build;
`npm run lint` runs ESLint.

## What this is, architecturally

The source wasn't a hand-authored site — it's a generated Elementor page
with ~966KB of CSS (3 real `<style>` blocks: a small custom-property
block, a theme block with `@font-face` rules, and an 818KB "combined CSS"
bundle covering Elementor core/widgets/plugins) keyed almost entirely to
auto-generated element IDs/classes (`elementor-element-xxxxxxx`). SingleFile
captured **zero `<script>` tags** — none of the site's original JavaScript
exists in the source file.

Given that, the conversion strategy (confirmed with the requester before
building) was:

1. **Keep the extracted CSS as global CSS, not Tailwind.** Hand-porting
   818KB of ID-scoped generated rules to Tailwind utilities isn't
   practically achievable without high risk of visual drift, and provides
   no real benefit. `src/styles/base.css`, `theme.css`, and `combined.css`
   are the original 3 stylesheets, byte-for-byte except that every
   embedded `data:` URI (fonts, background images) was rewritten to point
   at extracted files in `public/`. Tailwind is available for the small
   amount of genuinely new UI (mobile nav, popup) but isn't used to
   restyle the ported content.
2. **Reimplement interactivity from scratch.** Since no JS was captured,
   the following are original React implementations, not ports, built by
   inspecting the surrounding CSS/markup for the intended behavior:
   - `TextRotator.tsx` — cycles the hero's rotating word using the exact
     `.kd-text-rotator__item.is-active`/`is-hidden` classes the CSS
     already animates.
   - `LogoCarousel.tsx` — real `swiper` (npm) carousel replacing the
     frozen, JS-less Swiper DOM SingleFile captured.
   - `SiteHeader.tsx` mobile nav — the original theme CSS for the
     mobile nav overlay (`.kd-nav-menu-widget .nav-primary`) is intact
     in `combined.css`; it was driven by inline `opacity`/`visibility`
     set by JS, which is now done via React state. The hamburger icon's
     bars didn't exist in the captured DOM at all (button was empty —
     the theme's JS injected them at runtime) and are new markup/CSS
     (`styles/custom.css`).
   - `BackToTop.tsx` — scroll-to-top with a scroll-progress ring;
     visibility/progress were originally JS-driven inline styles.
   - `ContactPopup.tsx` — the "Get started" slide-in panel. No close
     button existed in the captured DOM (the popup plugin likely
     injected one at runtime); one was added for usability.
   - `NewsletterForm.tsx` / `ContactForm.tsx` — the 3 Contact Form 7
     forms in the capture. SingleFile only saves rendered HTML, so
     there's no backend to submit to; submission is stubbed locally
     (shows a local success message, no network call).
3. **Preserve markup structure for everything else.** The 11 static
   content sections (`src/components/sections/*.tsx`) and the header/
   footer chrome are a faithful structural port of the original markup —
   same classes, same nesting, same inline styles — generated by walking
   the parsed HTML and converting each node to JSX (attribute
   renaming, `style` string → object, `data:` URI rewriting). This is
   why they preserve the original `elementor-element-*` classes: those
   are exactly what `combined.css` targets.

## Assets

All 46 unique `data:` URIs (images + fonts, deduplicated by content
hash) were extracted to `public/images/` and `public/fonts/`, and every
reference — in the HTML and inside the 3 CSS files — was rewritten to
point at them. The favicon became `src/app/icon.png` (Next.js's
automatic favicon convention).

Most images are plain `<img>` tags with the original `width`/`height`/
`src`/`class` attributes, not `next/image` — the source page positions
many images via complex Elementor-generated absolute/flex CSS, and
swapping every one to `next/image` risks fighting that layout for no
real benefit here. A few simple, well-defined cases (header/footer logo,
carousel logos) do use `next/image`.

## `/homepage2` (Sasflo) — audit notes

Same approach as the Sierra page (CSS kept global — 36 `<style>` blocks
concatenated in original order into `src/styles/homepage2/combined.css`,
~450KB → ~172KB after rewriting embedded `data:` assets; interactivity
rebuilt from scratch since no JS was captured). Specific to this page:

- **A hidden SEO spam link was found and removed.** The capture
  contained a zero-size, off-screen `<div>` (clip-rect hidden, disguised
  as an Elementor "HTML widget") linking to an unrelated gambling
  affiliate site. This is link-spam cloaking, not real page content —
  it was deliberately excluded, not ported. See `src/app/homepage2/page.tsx`.
- **Two content gaps in the source itself** (not a conversion bug):
  SiteGround Optimizer's lazy-content stripping removed the collapsed
  content of both the FAQ accordion (4 of 5 answers) and the process-step
  tabs (3 of 4 step images) from the HTML — only whatever was open/active
  at capture time survived. `AccordionFaq.tsx` and `ProcessTabs.tsx`
  render clearly-marked placeholders for the missing ones rather than
  fabricated text.
- **The header's "Home" mega-menu was simplified to a plain link.** It
  originally opened a rich dropdown showcasing *other* demo homepages of
  the same theme (with thumbnail images) — not content of this page, so
  not worth reproducing. The "Pages"/"Blog" dropdowns are real and kept
  (desktop: pure CSS `:hover`, already in the extracted CSS; mobile: a
  new click-toggle panel, see `Header2.tsx`).
- **Only the primary header is rendered.** The original had a second,
  initially-hidden "sticky-up" header clone meant to be swapped in by JS
  on scroll; that swap logic wasn't captured, so it's dropped.
- The GSAP `SplitText`-style entrance animations (hero heading, footer
  heading — each letter in its own `<div>`) were flattened to plain text.
  They're one-time page-load reveal animations, not core interactivity.
- The video lightbox (`VideoLightbox.tsx`) is a plain YouTube-iframe
  modal replacing the original Venobox lightbox, which wasn't captured.

## Known limitations / things a reviewer should check

- **Nav links** (`Solutions`, `Pricing`, `News`, `Help`, `Contact`,
  footer links) point to local paths (`/services`, `/pricing`, ...)
  mirroring the original site's structure, but **only the homepage was
  captured** — those routes don't exist in this project and will 404.
- **Forms don't submit anywhere real.** No backend was captured; all 3
  forms show a local "thanks" message on submit instead of calling an
  API.
- **The sticky feature quick-nav** (`FeatureStickyNav.tsx`, the
  eCommerce/Client management/Inventory management bar) uses native CSS
  `position: sticky` with real `#section1/2/3` anchor links, which works,
  but the original likely used JS to keep it pinned across all three
  feature sections rather than just its own (short) container height —
  native sticky will unstick sooner than the original probably did.
- **`data-id`/`data-element_type`/`data-settings` Elementor attributes**
  were kept on the mechanically-converted sections for traceability back
  to the source. They're inert (Elementor's JS that reads them isn't
  present) and safe to strip if you want cleaner markup.
- Body UA-sniffing classes (`e--ua-blink`, `e--ua-chrome`, `e--ua-webkit`)
  were kept as static defaults from the capture rather than detected at
  runtime; they only matter if some CSS rule specifically depends on them.
